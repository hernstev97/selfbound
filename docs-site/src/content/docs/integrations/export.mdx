Your data is yours, and you can get all of it out at any time. The quickest way is **Settings → Data export**. There are four ways in total, depending on what you need.

| You want | Use |
|---|---|
| Everything, readable and complete, in one ZIP | [Data export](#data-export-in-settings) |
| The same ZIP without opening the app | [The export script](#automate-the-export) |
| A copy in Convex's own format, or one you can restore | [Database export](#export-the-whole-database) and [nightly backups](#nightly-backups) |
| Some issues or pages as Markdown or a list | [An AI agent](#ask-an-agent) |

## Data export in Settings

Open **Settings → Data export** and choose **Export**. Your browser reads all data and downloads `selfbound-export-<date>.zip`. The ZIP has three folders:

- **`json/`** is the complete copy. Every table that holds your data is one file (`json/issues.json` and so on) with the rows as stored, trash included, one row per line. `json/manifest.json` records the format (`selfbound-export`), the version (1), the time of the export, the number of rows per table and every stored file with its path. Files that could not be read are listed under `missingFiles`, so you can see whether the copy is complete.
- **`markdown/`** is the readable copy. `README.md` gives an overview of teams, statuses, projects, labels, sprints and recurring issues. Every issue is one file with its properties, description, relations, sub-issues, pull requests, comments and history. Every knowledge page is one file too, in folders that follow the page tree. Deleted issues and pages are under `trash/`. Images link to the files in the ZIP.
- **`files/`** holds the images from descriptions, comments and pages, and the team logos.

The app reads the data table by table while you wait, so changes made during the export may be in it only partly. For a consistent copy, use the script below.

**Not exported:** agent key hashes and prefixes, OAuth data of connected AI tools, and push subscriptions of your devices. Derived data such as search indexes, caches and running state (counters, inbox, rate limits) are left out too, because Selfbound rebuilds them.

<Aside type="note">
**Re-import is not available yet.** The JSON is complete and versioned so that a later version can import it. Until then, the ZIP is for reading and keeping, not for restoring. To restore an instance, use a [nightly backup](#nightly-backups).
</Aside>

<Aside type="caution">
The ZIP contains all your data unencrypted. Store it somewhere safe and delete copies you no longer need.
</Aside>

## Automate the export

The script `tooling/export/index.mjs` in the Selfbound repository builds the same ZIP from a Convex export, without the app. Use it for scheduled exports or for the decrypted nightly backup:

```sh
node tooling/export/index.mjs --from ~/selfbound-export.zip
```

`--from` takes a ZIP made with `convex export --include-file-storage` (see below). Without that option, the export has no images and the manifest lists them under `missingFiles`. Without `--from`, the script exports the local development backend first. The result lands in `~/.local/share/selfbound/exports/`; `--out <folder>` chooses another folder. Because it reads a Convex export, this copy is consistent.

## Export the whole database

Convex can export a deployment as a ZIP file. This is the export the nightly backup uses, and it contains everything: issues with descriptions, comments and history, teams, labels, projects, sprints, knowledge pages, and the uploaded images and team logos.

You need a checkout of the Selfbound repository with dependencies installed, and a production deploy key from the Convex dashboard. With your instance set up as in [Self-hosting](/start/self-hosting/) (deploy key in `~/.config/selfbound/convex-deploy-key`), run:

```sh
node tooling/cloud.mjs export --include-file-storage --path ~/selfbound-export.zip
```

Without the Selfbound tooling, run the Convex CLI in the `backend` folder with the deploy key in the environment:

```sh
cd backend
read -rs CONVEX_DEPLOY_KEY && export CONVEX_DEPLOY_KEY   # paste the production deploy key, then Enter
pnpm exec convex export --include-file-storage --path ~/selfbound-export.zip
unset CONVEX_DEPLOY_KEY
```

The ZIP holds one JSONL file per table (one JSON document per line) and a folder with the stored files. The data is in Selfbound's internal format: for example, issue descriptions are stored in a separate table from the issues. The tables and fields are defined in [`backend/convex/schema.ts`](https://github.com/hernstev97/selfbound/blob/main/backend/convex/schema.ts). The same ZIP can be imported into another Convex deployment with `convex import`.

<Aside type="caution">
The export contains all your data unencrypted. Store it somewhere safe and delete copies you no longer need.
</Aside>

## Nightly backups

The Selfbound repository includes a GitHub Actions workflow that backs up your production deployment every night at 03:30 (Berlin time). It is meant for operators and disaster recovery, not for reading your data, but it is a complete copy:

- Each backup is the database export described above.
- Before it is stored, it is restored into an empty backend and compared table by table and file by file.
- It is encrypted with [age](https://age-encryption.org); only the holder of your private key can open it.
- Daily backups are kept for 30 days, Sunday backups for 90 days, as artifacts of the workflow run.
- **Settings → Ops** shows when the last backup reported in.

The workflow does nothing until you add a deploy key and your public age key as secrets. In a public repository, workflow logs and artifacts are public: the backup itself stays encrypted, but table names and document counts are visible. Run the backup from a private copy of the repository if that matters to you.

Setup, restore and the quarterly decryption test are described in the [backup guide on GitHub](https://github.com/hernstev97/selfbound/blob/main/docs/backup.md).

Not part of a backup: environment variables such as secrets and tokens (keep them in a password manager), and videos, which are links to Google Drive rather than files in Selfbound.

## Ask an agent

An AI agent connected to Selfbound over MCP can read any issue with its full description, comments, relations, sub-issues, linked pull requests and recent history, and any knowledge page. That makes it a practical way to export a slice of your data in a format you choose, for example:

> Write every open issue of team ACME to a Markdown file, one section per issue, with its description and comments.

This is not a complete export. Lists and searches leave out issues in the trash, return at most 100 issues per call (searches 50) and cannot page further, so split a large export by team, status, label or project. For everything, use the database export.
